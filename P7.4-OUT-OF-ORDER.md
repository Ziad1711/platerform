# P7.4 — Test ciblé des réponses réseau out-of-order

**Environnement :** jisra-test uniquement, Chrome headless + profil P6, application
locale sur `localhost:3000`, URL/clé publishable Test. Aucune requête navigateur
vers Production. Aucun changement du projet P7.

## 1. Défaut reproduit avant correction

Une réponse `rpc_dashboard_kpi_rollout` ancienne a été retenue au niveau HTTP
(CDP `Fetch`, stage `Response`), puis le kill switch a été activé.

| Élément | Valeur observée |
|---|---|
| Réponse retenue | version **95**, `kill_switch=false`, `selection_mode=v5` |
| Après activation du kill switch | page passée en `legacy` par expiration |
| Après libération de l’ancienne réponse | **`mode=v5`, version 95, kill=false** |

**Conclusion avant correction : FAIL.** Une réponse ancienne pouvait réactiver
V5 après le kill switch, alors qu’aucune nouvelle réponse de configuration
n’avait été acceptée.

## 2. Correction appliquée

Deux gardes dans `KpiRolloutProvider` :

1. `acceptsConfigVersion` : ignore toute version inférieure à la version
   maximale déjà reçue ;
2. séquence de requête (`requestSeq` / `minAcceptedSeq`) : lorsqu’une transition
   vers legacy survient (kill switch ou expiration), toute réponse dont la
   requête a démarré avant cette transition est ignorée.

La correction reste dans `lib/dashboard/use-kpi-rollout.tsx` et
`lib/dashboard/rollout.ts` ; aucune formule financière n’est modifiée.

## 6. Limite du scénario strict « ancienne après plus récente »

Le test navigateur n’a pas pu produire une **nouvelle réponse avant** l’ancienne
dans le même provider : React Query ne lance pas un second poll tant que la
réponse précédente est retenue (`continued-rollout` absent). Le scénario testé
est donc « ancienne réponse après kill switch/expiration », pas « ancienne après
nouvelle ».

La garde de séquence couvre néanmoins le cas « ancienne après nouvelle » :
toute réponse dont la requête est antérieure à la version/transition acceptée
est ignorée. Le test logique `acceptsConfigVersion` est **4/4 PASS** (nouvelle,
égale, ancienne, invalide).

## 7. Test déterministe concurrent A/B

Un test local `@tanstack/react-query` + fonctions pures a contrôlé l’ordre des
requêtes et réponses, sans navigateur supplémentaire :

- même clé de requête : deux `fetchQuery` concurrents → **un seul appel**
  (`sameKeyCalls = 1`) ; React Query déduplique la requête en vol ;
- clés différentes (session/boutique/rôle) : la réponse ancienne met à jour sa
  propre clé uniquement ; la clé récente conserve sa décision ;
- décision `acceptsRolloutEntry` : **A seq1/version10 rejetée après B
  seq2/version11**, y compris si B est une transition legacy ;
- version ancienne après nouvelle : rejetée ;
- même version, séquence plus récente : acceptée ;
- payload kill switch : résolution `legacy`.

**12/12 contrôles PASS.**

Conséquence : deux réponses concurrentes de la **même clé** ne peuvent pas
arriver dans l’ordre inverse au sein d’un même provider, car React Query
n’émet qu’une requête en vol. Les autres chemins (session, boutique, rôle,
onglet) utilisent des clés ou des clients distincts : une ancienne réponse ne
peut pas écraser la clé courante. Le scénario DOM ancienne réponse après
kill/expiration reste validé (legacy, aucune réactivation V5).

## 8. Verdict

**PASS** pour la garde anti-réponses obsolètes, avec preuve bornée :

- défaut réel de réactivation reproduit puis corrigé ;
- ancienne réponse après kill/expiration : **legacy**, aucune réactivation V5 ;
- réponses lecteur/financières tardives : **aucune donnée interdite** ;
- concurrence A/B même clé : **impossible par déduplication React Query**,
  démontrée par `sameKeyCalls = 1` ;
- clés session/boutique/rôle distinctes : **isolées** ;
- décisions pures A/B : **12/12 PASS**.

Limite exacte : le test A/B est un test déterministe de la couche React Query
et des fonctions de décision, pas une capture réseau de deux réponses
concurrentes dans le même DOM — cette concurrence n’est pas produite par React
Query pour une même clé.

État final Test : configuration OFF, 0 cohorte, 0 événement, rôle viewer
restauré, 23 fonctions KPI, 6 triggers KPI, 2 jobs KPI. Aucune modification
Production ou projet P7.
